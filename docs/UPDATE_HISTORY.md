## 현재 배포 기준선

- 최신 배포는 v0.0.43. [당사자 전용 조작·색상·잔디 갱신·슬래시 종료](GARDEN_CONTROLS.md)를 적용했다. v0.0.30의 정규화·이관 기록은 [DB 명세](DATABASE_NORMALIZATION.md)를 따른다.

- 원씽 잔디와 기존 등록·완료 조작이 존재한다. 이 문서 작성이 전체 기능 재검증을 뜻하지 않는다.
- 2026-09-11 v0.0.1~v0.0.19 구현·admin-dev 사용자 QA를 완료했다. 정시 안내 전환은 추가20~22로 기록했다. 상세 범위와 제한은 [릴리스 기록](RELEASE_V001_V019.md)을 따른다.
- 최초 해석 파일럿의 배포 식별자는 역사 기록이다. 초기 배포·소스 해시는 `.omx/qa/v001-v019/release.json`에 보존한다. 최신 관리자 권한 배포는 [권한 정책](ADMIN_ACCESS.md)을 따른다. [최초 파일럿 기록](LLM_PILOT_RESULTS.md).
- 아래 계획 번호를 기존 배포에 소급하지 않는다.

## 변경 하나에 버전 하나

버전 자체가 작업 식별자다. 한 버전은 사용자에게 관찰 가능한 결과 하나를 완성하는 단위다. 같은 결과에 필요한 화면·코드·데이터·검증은 함께 포함하고, 독립적인 결과는 다른 버전으로 나눈다. 선행 버전에 의존할 수 있지만 선행 조건이 갖춰지면 해당 변경만 배포하고 검증할 수 있어야 한다.

2026-09-11 사용자의 실행 요청으로 v0.0.1~v0.0.19를 구현하고 admin-dev에서 사용자 프로필로 검증했다. 추가 요청인 공통 원씽·후기 정시 안내와 기존 Slack 반복 알림 전환을 v0.0.20~v0.0.22로 기록한다. v0.0.23~v0.0.25는 townhall 연결, v0.0.26은 관리자 권한 보호로 추가 구현했다. 이후 버전은 계획이다. [구현·QA 근거와 한계](RELEASE_V001_V019.md)를 함께 읽는다.

각 버전의 실제 사용자 조작 QA는 그 버전에 포함한다. 문서 작성·테스트 실행만 따로 기능 출시로 세지 않는다. v0.0.69은 제품 배포가 아니라 사업 가설 검증이며 문서 작성만으로 완료되지 않는다. 유료 구현이 결정되면 결제·환불 같은 선행 기반도 별도 원자적 버전으로 추가한다. 문자 대체 발송은 필요 여부 결정 후 별도 버전으로 추가하며 카카오 실패 시 자동 적용하지 않는다.

운영 정책 배경은 [운영 로드맵](SERVICE_ROADMAP.md)을 따른다. 30명·50명과 4주 관찰은 제안이며 확정 기준이 아니다.



## 현재 우선순위와 재정렬 기준

이 절은 현재 목록의 배치 요약이다. 판단 순서, 예외, 출시 조건은 [제품 우선순위와 운영 원칙](PRODUCT_PRINCIPLES.md)을 따른다.

1. 원씽 등록·완료·후기·휴식을 정확히 기록하고, 풍부한 반응과 회원 간 샤라웃으로 이어지는 기본 흐름. 첫 완료·첫 후기도 샤라웃으로 축하한다. 버튼은 매번 강제하지 않고 애매할 때 확인하며 자동 처리 범위는 검증 후 확정한다.
2. 다음 구현은 목표·후기 수정(v0.0.41~42)과 최신 안내글 발행·신입 전달(v0.0.44~44)이다. 핵심 기록의 정정과 첫 참여 안내를 외부 채널 확장보다 먼저 완성한다.
3. 회원 상태를 바탕으로 후기·원씽 누락을 챙기고, 습관이 끊기기 전 먼저 원씽 대화를 시작한다. 중지·동의·카카오 전달과 접촉 빈도의 균형을 함께 갖춘다.
4. Slack 안에서 삭제·온보딩·Silo 운영을 먼저 보완한다. 카카오(v0.0.53~43)와 홈페이지(v0.0.56~48), 카카오 수신(v0.0.61~50)은 후순위로 보류한다.
5. 정원·미참여 제외·경쟁·수익화는 필요한 정책과 선행 기능을 확인한 뒤 진행한다.

새 요구마다 사용자 영향, 현재 문제의 시급성, 선행 조건, 검증 가능성을 비교해 넣는다. 정책 미정인 버전이 앞에 있더라도 임의로 정책을 확정하지 않는다. 다른 버전을 먼저 진행하기로 하면 계획 번호와 모든 현재 참조를 함께 조정하고 이력에 구번호→신번호를 남긴다. 배포된 버전 번호는 고정한다.

### 풍부한 반응과 먼저 다가가기

등록·완료·후기 반응은 장식이 아니라 관계 형성의 핵심 흐름이다. 그래서 이모지·응원 버전을 각 기록 기능 직후에 배치했다. 고정 안내 문구와 이모지는 우선 템플릿으로 처리하고 개인화가 필요한 경우에만 LLM 사용을 검토한다. 실제 사람의 반응처럼 위장하지 않는다.

카카오 메시지로 등록하는 기능은 나중 단계다. 카카오 알림 발송, 홈페이지에 카카오 프로필을 적는 것, 카카오에서 메시지를 수신하는 것은 별개다. 현재 수신 API·연결 자격이 확인되었다고 가정하지 않는다. 애매한 말은 카카오 안에서 확인하고 일반 잡담까지 Slack에 자동 공개하지 않는다.

## 기록 규칙

- 변경마다 버전·결과 하나·완료 조건·선행 조건·상태를 기록한다.
- 계획 → 구현 중 → 검증 → 배포를 구분하고 실제 배포 시 식별자·날짜·검증 근거·남은 제한을 추가한다.
- 독립적인 변경이 두 개면 버전을 나눈다. 같은 결과에 필요한 구현을 파일이나 기술 계층별 버전으로 쪼개지는 않는다.
- 새 항목은 우선순위에 따라 삽입하고 미출시 계획 번호·선행 참조를 함께 재정렬한다. 날짜·사유·구번호→신번호를 기록한다. 실제 출시한 번호는 변경하거나 재사용하지 않는다.
- 버전별 문서 기록은 모든 변경의 공통 작업이다. 문서 편집마다 별도 제품 버전을 발급하지 않는다.
- 인터뷰가 끝나기 전 구현으로 넘어가지 않는다. 외부 공지는 별도 요청이 있을 때만 전송한다.
