# v0.0.44 후기 입력·편집 신뢰성 개선

## 문제와 원인

`후기:\n9/14: 완료. 교수님께 예약 메세지를 걸어두었는데 어떤 피드백이 올지...` 형식이 완료·후기로 저장되지 않았다. 실제 이벤트 수신은 있었지만 날짜 있는 당일 후기를 수정 확인 경로로 보내고 모델 해석에 의존했다. 원문에는 편집 이력도 있었으며 기존 message_changed는 무시했다.

## 동작

- 명시적 후기/회고 헤더, 날짜와 맨 앞의 수행 상태를 먼저 읽는다. 줄바꿈·CRLF·전각 콜론·일부 마크다운 헤더, YYYY-MM-DD/YYYY.MM.DD/M/D/M.D/M월D일을 지원한다.
- 명확한 **당일 첫 후기**만 자동 저장한다. 동일한 작성자·채널·날짜의 기존 목표가 있어야 하며 revision으로 동시 수정 충돌을 막는다.
- 상태만 있는 `후기: 완료.`는 완료 상태만 반영한다. 후기를 제출한 것으로 만들거나 첫 후기 축하를 보내지 않는다. 과거/충돌 확인 단계에서도 같은 구분을 유지한다.
- 과거 날짜, 기존 후기 덮어쓰기, 휴식/수행 상태 충돌은 당사자 확인을 거친다. invalid/future/multi-date는 저장하지 않는다.
- `완료. 하지만 절반만...`, 정정·예문·메타 질문 등 모순/불확실한 본문은 자동 완료하지 않는다. 거절된 헤더의 날짜가 명확하지 않으면 오늘로 추측한 수정 버튼을 만들지 않는다.
- 자유로운 후기 문장은 확인 단계로 이어질 수 있다. 본문에 날짜/숫자가 있고 파싱이 불명확하면 날짜·상태를 다시 요청한다. 보수적 처리로 일부 정상 문장도 추가 확인이 필요할 수 있다.
- Slack 사용자 메시지 편집은 바깥 이벤트의 채널과 원래 메시지 작성자·timestamp·thread를 보존한다. 편집 timestamp는 freshness 및 별도 중복 키로 사용한다. 봇이 잔디 메시지를 갱신한 이벤트는 재처리하지 않는다.
- 명시적 후기/수정 요청이 없는 일반 Slack 글 편집은 자동 목표 변경하지 않는다. 후기와 목표의 원본 데이터·다른 날짜·알림 설정은 영향을 받지 않는다.

## 검토와 한계

초기 검사 통과 후 독립 검토에서 모순된 완료, 확인 경로의 후기 덮어쓰기, 채널 유실, 지원하지 않는 날짜의 잘못된 확인창을 추가 발견했고 수정·회귀로 잠갔다. 목표/코드/보안/실행/맥락의5개 검토는 보고된 결함의 유한 범위 종결을 확인했다. 최종 작은 변경도 별도 검토한다. commit별 결과와 실제 배포·원문·복구 근거는 비공개 `.omx/qa/reflection-routing/`에 있다.

모든 자연어 엣지케이스의 원천적 제거를 보장하지 않는다. 확인 단계는 의도적 안전장치다. LLM 오류율0, Slack 전달100%, 외부 API와 DB의 분산 원자성을 주장하지 않는다. 알려진 형식은 결정적 파싱, 불명확한 것은 확인/질문, 과거 기록은 명시 날짜와 revision으로 보호한다.
