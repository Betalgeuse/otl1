# 직장인 초대 전 회원 데이터 점검

이 문서는 이관 전 점검 기록이다. 이후 완료한 v0.0.30의 현재 구조는 [DATABASE_NORMALIZATION.md](DATABASE_NORMALIZATION.md)를 따른다.

2026-09-11 운영 Neon DB를 읽기 전용으로 점검했다. 스키마·회원 상태를 변경하지 않았다.

## 확인한 운영 상태

- 실제 테이블: profiles, goals, community_days, community_events, community_milestones, community_preferences, community_records.
- profiles 4행, legacy goals 9행, community_days 13행(QA 포함), community_events 19행. daily-scrum 기록을 가진 고유 Slack 사용자 4명. Slack 전체 회원 수를 뜻하지 않는다.
- 로컬 migrations/002~004의 memberships·invites는 현재 연결된 운영 DB에 없다. 초대 기능 설정도 비활성이다. 따라서 월 초대권·초대자 관계가 현재 운영 DB에서 관리된다고 볼 수 없다.
- 모든 현재 테이블은 복합 기본키가 있다. 확인된 외래키는 goals → profiles 한 개다. community 계열에는 회원을 참조하는 외래키가 없다.
- daily-scrum의 비어 있지 않은 community_days 목표를 legacy goals와 비교하면 3건은 legacy 없음, 1건은 목표 본문 다름, 완료 여부 차이 0건. 반대 방향으로 legacy만 있고 community에 없는 기록은 0건. 어느 쪽을 덮어쓸지는 원문·변경 이력 대조 후 판단해야 한다.

## 정규화 판단

현재는 작은 MVP용 혼합 모델이다. 날짜별 목표·후기·상태는 같은 회원·채널·날짜 키에 종속하므로 한 행에 둔 자체가 정규화 위반은 아니다. 변경 전 스냅샷도 감사·되돌리기를 위한 의도적 중복이다. JSONB 사용만으로 정규화 여부를 판정하지 않는다.

문제는 회원의 기준 엔터티와 관계 제약이 부족하고, 목표가 goals와 community_days에 이중 저장되며, 설정·발행·발송 기록을 범용 JSONB records에 함께 담아 핵심 관계를 DB가 강제하기 어렵다는 점이다. ‘3NF까지 정규화 완료’라고 주장할 근거가 없다. 현재 읽기·최근 쓰기는 확인했지만 백업 복구, 부하, 전체 데이터 무결성을 검증한 것은 아니다.

## 직장인 확대 전 권장 순서

1. 목표·후기 수정 구현에 앞서 실제 원본 경로와 두 저장소의 불일치를 대조한다. community_days를 운영 원본으로 삼는 안을 검토하고 legacy는 파생 조회용으로 제한하거나 제거한다. 원문을 확인하지 않고 일괄 동기화하지 않는다.
2. workspace_members에 Slack 식별자·회원 상태·가입 정보를 모으고 기존 참여자를 보존하며 연결한다. 이후 새 관계에 외래키를 적용한다. 기존 회원을 초대자 미상이라고 삭제하지 않는다.
3. LinkedIn 연결을 도입한다면 member_external_profiles에 플랫폼·정규화 URL·확인 상태·확인 주체·시각을 둔다. 프로필 링크만으로 본인·재직을 확인했다고 표시하지 않는다. 공개 범위와 본인의 수정·삭제 권한을 정한다. 직장명을 고유 식별자로 쓰지 않는다.
4. 회사 소속 이력, 초대자 관계, Silo 구성원 이력을 서로 분리한다. 초대자와 같은 Silo 정책이 있더라도 회사=초대자=팀으로 합치지 않는다. 이직해도 과거 성취와 소속 이력을 보존한다.
5. 가이드 발행본·회원별 전달 기록은 별도 구조로 만든다. 회원·발행본·게시물 관계와 재전송 제한을 DB가 검증하도록 한다.

권장 엔터티: workspace_members, member_external_profiles, organizations, member_affiliations, silos, silo_memberships, invitations, community_days, guide_versions, guide_deliveries. 이를 한꺼번에 모두 도입하지 않고 관련 사용자 기능을 구현할 때 필요한 부분부터 전환한다. 홈페이지·카카오를 앞당길 필요는 없다.

## 먼저 정할 운영 기준

- LinkedIn: 회원 프로필 연결인지, 초대 후보 담당자 배정인지 사용자 확인 대기. 둘은 다른 데이터 모델이다. 후자면 후보·담당자·접촉 상태를 회원 원장과 분리하고 가입 후 연결한다.
- 초대 정원: 월1장과 현 안내글의2명 중 적용 정책 확정 필요.
- 직장인의 원씽 단위: 업무 목표와 개인 성장 목표의 허용 범위, 회사 기밀이 들어간 목표의 공개 범위.
- 오전10시 등록·오후6시 후기: 모든 회원의 마감인지 공동 안내 시각인지 구분. 늦은 가입·휴가·교대근무를 미참여로 자동 판정하지 않는다.
- Silo: 직장, 초대 관계, 관심사 중 배정 기준과 중복 소속·이동 방식. 초대자 신뢰와 경쟁 지표를 혼동하지 않는다.

이번 문서는 점검 결과와 제안이다. v0.0.30~33의 핵심 수정·가이드 우선순위 및 현재 배포 v0.0.29는 변경하지 않았다.
