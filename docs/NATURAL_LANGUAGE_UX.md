# 커맨드 없이 쓰는 원씽 UX

2026-09-11 후속 구현: [v0.0.1~v0.0.19 릴리스·검증 기록](RELEASE_V001_V019.md)을 먼저 참고한다. 아래는 작성 당시 파일럿·설계 기록이다.

현재 배포: 봇을 채널에 초대한 뒤 Slack 자동완성으로 `@OT1L 목표 문장`을 태그하면 스레드 초안과 `등록`·`취소` 버튼이 표시된다. 등록 전에는 DB에 저장하지 않는다. `/one`은 기존 호환 경로다. 봇이 참여하지 않은 채널의 멘션은 Slack이 이벤트를 보내지 않는다.

상태: 설계 제안. 자연어 입력은 아직 배포되지 않았다. 현재 `/one` 사용법은 [설정·사용 안내](SETUP.md)에 있다.

## 첫 버전의 목표

커맨드 대신 **평문과 눈에 보이는 버튼**으로 등록·완료·관리를 끝낸다. 처음부터 모든 대화의 의도를 자동 해석하는 시스템을 만들지 않는다. 질문에 평문으로 답하는 체크인과 자유로운 AI 질의는 별도 기능이라는 벤치마크 결과를 반영한다. [비교 근거](COMMUNITY_BENCHMARK.md#자연어에-관한-중요한-구분)

## LLM을 붙이는 편이 좋은가

**목표를 함께 정리하고 이전 대화를 이해하는 서비스로 가려면 LLM 도입을 추천한다.** 다만 자연어 문장을 받는 것만으로 LLM이 필요한 것은 아니다. 다음 구분은 이 서비스에 대한 설계 판단이다.

| 원하는 동작 | LLM의 역할 |
| --- | --- |
| “오늘 책 10쪽 읽기”를 그대로 등록 | 필수 아님. 평문 입력과 확인 버튼으로 처리 |
| “어제 못한 걸 오늘은 절반만 해볼래” | 이전 목표를 찾아 어떤 변경인지 해석하고 초안 제안 |
| “운동도 공부도 해야 하는데 뭘 먼저 할까” | 필요한 질문 하나를 하고 오늘의 원씽 후보를 함께 좁히기 |
| “다 했어” | 완료 요청으로 해석할 수 있지만, 어느 목표인지와 사용자 확인은 별도 |
| 초대권·날짜·소유자·잔디 상태 판정 | LLM에 맡기지 않음. 서버와 DB의 고정 규칙 사용 |

추천 구조는 `사용자 문장 → LLM의 해석·변경안 → 서버 검증 → 사용자 확인 → 기존 상태 변경 코드`다. 모델에는 본인의 현재 목표와 필요한 대화만 제공한다. 모델이 다른 사용자 ID를 내놓거나 모르는 목표를 지정하면 거부한다. 확신이 없으면 질문하거나 원문 입력·버튼 흐름으로 돌아간다.

모델 출력은 자유 문장에서 다시 추출하기보다 의도·대상 목표·변경안을 정해진 구조로 받는 편이 구현하기 쉽다. Workers AI도 JSON Mode와 function calling을 제공한다. 이는 사용 가능한 구현 수단의 예이며, 특정 모델이나 공급자를 선택한 것은 아니다. 형식이 맞는 JSON이라도 의도와 대상이 올바른지는 별도로 검증해야 한다. [JSON Mode](https://developers.cloudflare.com/workers-ai/features/json-mode/), [Function calling](https://developers.cloudflare.com/workers-ai/features/function-calling/)

운영 모델을 결정하기 전에 API 키를 추가하거나 실제 대화를 외부 LLM에 보내지 않았다. 모델 선택과 비용·지연 평가는 한국어의 부정 표현, 과거 날짜, 여러 목표, 타인 언급을 포함한 예시로 비교한 뒤 한다. 기본 등록·완료 경로는 모델 장애 중에도 사용할 수 있게 유지한다.

## 권장 기본 흐름: 채널에서 봇을 태그해 입력하고 공개 등록

```text
참여자: @원씽 잔디 오늘은 퇴근 후 책 10쪽 읽을게요.

봇: 오늘의 원씽으로 아래 문장을 등록할게요.
    “오늘은 퇴근 후 책 10쪽 읽을게요.”
    공개 위치: #ot1l-daily-scrum
    [등록] [고치기] [취소]

등록 후:
    오늘의 원씽 · 작성
    [완료] [수정] [내 잔디]
```

사용자가 쓴 원문을 먼저 보존한다. 문장을 임의로 더 야심찬 목표로 바꾸거나 성공 기준을 만들어 넣지 않는다. 첫 단계에서는 문장을 그대로 받는 데 생성형 AI가 필요하지 않다. 변경 권한은 등록·완료 버튼에 둔다.

채널 멘션을 선택하면 명령어를 외울 필요 없이 누구나 같은 흐름을 볼 수 있다. 봇은 멘션이 포함된 문장을 초안으로만 제시하고, 작성자가 등록 버튼을 눌러야 저장한다. 잡담이나 여러 목표가 섞인 문장은 등록하지 않고 한 가지를 다시 묻는다.

## 표현별 처리 원칙

아래는 구현해야 할 동작의 예시이며 현재 지원하는 자연어 명령 목록이 아니다.

| 입력·상황 | 제안 동작 |
| --- | --- |
| 오늘의 목표 질문에 한 문장 응답 | 원문을 초안으로 제시하고 공개 등록 확인 |
| “다 했어” | 현재 대화에 연결된 오늘 목표를 보여주며 완료 확인. 참조할 목표가 없으면 먼저 선택 |
| “아직 못했어” | 완료하지 않음. 필요하면 짧은 진행 메모 제안 |
| “10쪽 말고 5쪽으로 바꿀래” | 기존 내용과 변경안을 나란히 보여주고 수정 확인 |
| “어제 목표 말한 거야” | 날짜를 명확히 보여주고 해당 기록 선택. 오늘 칸을 자동 변경하지 않음 |
| “운동도 하고 책도 읽고 싶어” | 오늘 가장 중요한 하나를 선택하도록 질문 |
| “이 말은 목표가 아니라 그냥 얘기야” | 초안을 취소하고 기록을 만들지 않음 |
| “지민이도 완료했대” | 타인의 완료 상태를 바꾸지 않음 |

첫 단계에서는 등록은 평문, 수정·완료는 버튼을 기본으로 한다. 후속 단계에서 이런 자유로운 수정·완료 요청을 추가하되, 해석 결과를 확인한 뒤 기존의 동일한 상태 변경 함수를 호출한다. 모델을 쓰더라도 DB 수정 권한을 모델에 직접 넘기지 않는다.

## 관리 화면

OT1L 앱 홈의 위쪽에 오늘의 상태와 가장 필요한 버튼만 둔다.

```text
내 원씽
오늘: 퇴근 후 책 10쪽 읽기
상태: 작성
[완료] [수정]

내 잔디 · 최근 기록
[날짜 선택] [색상 설정]
```

개인 앱 홈은 사용자가 같은 위치에서 자신의 기록으로 돌아오는 데 맞는 Slack 화면이다. 홈에서 연 입력 모달과 채널 카드가 같은 목표를 가리키게 한다. [App Home 문서](https://docs.slack.dev/surfaces/app-home/)

등록 전에는 빈 목표나 가짜 진행도를 보여주지 않고 **오늘의 원씽 작성** 버튼을 제공한다. 이전 기록을 찾는 데 날짜 형식의 명령을 요구하지 않도록 날짜 선택 UI를 제공한다. 이미 공개된 목표는 홈에도 공개 위치를 표시한다.

## 다음 구현 범위

### 1a단계: 커맨드 없이 오늘 등록·완료하기

- OT1L 메시지 탭에서 평문 초안 받기.
- 공개 위치를 명시한 등록·수정·취소 버튼.
- 사용자·날짜별 공개 카드 하나, 완료 시 같은 카드 갱신.
- `/one`은 기존 사용자용으로 유지하되 시작 안내의 주 경로에서는 제외.

### 1b단계: 개인 관리 화면

- 앱 홈에서 오늘 목표와 잔디, 날짜 선택, 색상 설정.
- 1a의 사용성을 먼저 확인한다. 개인 홈 전체를 만들기 전에도 DM과 기존 공개 카드로 등록·완료가 가능해야 한다.

### 2단계: 방향과 실천 연결

- 한 개의 활성 주간 목표와 완료 기준.
- 일일 원씽이 그 목표와 연결되는지 사용자가 선택.
- 주간 회고 세 문장과 다음 목표 조정.

### 3단계: 필요가 확인된 자동화

- 자연어 수정·완료 요청의 해석과 확인.
- 원하는 시간에만 받는 선택 알림.
- 초대제와 팀 범위가 확정된 뒤 팀 요약.

## 기술 변경 지점

| 변경 | 필요한 작업 |
| --- | --- |
| 채널 멘션 수신 | `/slack/events` 라우트, Slack URL verification·서명·이벤트 재전송 처리, `app_mention` 구독과 `app_mentions:read`·`chat:write` 권한 |
| 봇 대화·공개 카드 | `chat:write`, `chat.postMessage`·`chat.update`, 공개 대상 채널 ID 설정 |
| 개인 앱 홈 | Home tab 활성화, `app_home_opened` 수신, `views.publish` |
| 입력 확정 | 사용자에 묶인 초안 ID, 확정 버튼, 중복 확정 방지 |
| 같은 공개 카드 갱신 | 목표별 채널 ID·메시지 ts 저장, 저장 성공과 게시 성공 구분 |
| 주간 목표 | 일일 기록과 별도 엔티티. 첫 단계에서는 도입하지 않음 |

Slack 메시지 이벤트는 DM·공개 채널·비공개 채널별로 구독과 권한이 다르다. 첫 단계의 봇 DM 수신에는 `im:history`가 필요하다. 나중에 전용 공개 채널의 평문도 받으려면 `message.channels`와 `channels:history`를 검토한다. [메시지 이벤트](https://docs.slack.dev/reference/events/message/), [공개 채널 권한](https://docs.slack.dev/reference/scopes/channels.history/)

이 권한은 모든 직원의 개인 DM을 읽는다는 뜻이 아니라 봇이 참여하는 해당 대화의 이벤트를 받기 위한 것이다. [im:history 범위](https://docs.slack.dev/reference/scopes/im.history/) 앱이 받은 이벤트라도 설정한 워크스페이스·대화 범위에 맞는지 검사하고, 봇 자신의 메시지와 승인되지 않은 대화는 처리하지 않는다. 권한 추가·재설치는 구현 후 실제 Slack 앱에서 확인해야 한다.

현재 코드는 슬래시 명령과 버튼 요청만 처리하며 `/slack/events`와 개인 홈이 없다. 현재 응답은 `response_url`을 사용한다. 임의의 DM과 홈 버튼 흐름에는 같은 URL이 항상 주어지지 않으므로, 단순히 커맨드 파서만 바꿔서는 이 흐름이 완성되지 않는다. [상호작용 payload](https://docs.slack.dev/reference/interaction-payloads/block_actions-payload/)

## 구현 완료를 판단할 시나리오

1. 처음 온 사용자가 `/one`을 입력하지 않고 목표를 등록한다.
2. 등록 전에 원문과 공개 채널을 확인하고 취소할 수 있다.
3. 잡담·부정 표현·타인에 관한 문장이 완료 처리되지 않는다.
4. 같은 메시지 재전송·등록 버튼 중복 클릭으로 기록과 공개 카드가 늘지 않는다.
5. 다른 사람이 완료·수정·설정 버튼을 눌러도 작성자의 기록을 바꾸지 못한다.
6. 자정·월말·과거 기록 수정에도 Day와 날짜가 어긋나지 않는다.
7. DB 저장 후 Slack 게시가 실패하거나 결과가 불명확하면 복구 가능한 상태로 표시하고, 성공했다고 안내하거나 무조건 재전송하지 않는다.
8. 데스크톱뿐 아니라 실제 모바일 Slack에서 시작·등록·완료를 확인한다. 과거 조회는 1b단계에서 추가 검증한다.

문서 작성과 벤치마크 완료는 위 기능의 구현 완료가 아니다. 실제 사용자 입력과 화면에서 이 시나리오를 확인한 뒤 지원 기능으로 안내한다.
